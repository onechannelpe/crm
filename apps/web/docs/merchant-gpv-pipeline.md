# Merchant GPV import pipeline

This pipeline imports Culqi merchant GPV reports and produces device records,
monthly GPV, RUC attribution, and effective-dated targets for the sales
dashboards.

```text
xlsx bytes
  │
  ├─ LAND ─────► merchant_reports
  │              merchant_report_rejections
  │
  ├─ DECODE ───► SourceRow | Rejection
  │
  ├─ RESOLVE ──► AttributionVerdict per (ruc, month)
  │
  ├─ WRITE
  │   ├─ merchant_sales
  │   ├─ merchant_sale_gpv
  │   ├─ merchant_monthly_attribution
  │   └─ merchant_report_rejections
  │
  └─ READ ─────► dashboard projections
```

The upload is identified by the SHA-256 hash of its raw bytes. Re-uploading the
same file is a no-op.

Rows are decoded without database access. Attribution context is loaded once
for the batch, then the accepted rows, GPV values, attribution decisions, and
rejections are written in one transaction.

`merchant_monthly_gpv` is a SQL view over `merchant_sale_gpv` and
`merchant_sales`. The cohort offset is stored in `month_offset`, while
`realized_month` is generated by the database.

The pipeline must preserve these rules:

- A lead cannot receive credit for months before it existed.
- An import cannot move an existing sale to another month.
- An older cut cannot replace data from a newer cut.
- Changing a target cannot rewrite previous attainment.
- Re-importing the same file cannot create duplicate data.
- Executives can only read GPV for RUCs assigned to them.
- Manual attribution resolutions must appear on the RUC timeline.

`attributeMonth` checks the lead creation date against each sale in the month.
Existing attribution decisions are not replaced automatically.

`partitionBySaleMonth` rejects rows whose identity points to a different sale
month. `upsertGpv` only updates a value when the imported `cut_at` is newer than
or equal to the stored cut.

Targets are effective-dated. Dashboard reads use `targetAsOfMonth` and
`targetAsOfSaleMonth` instead of joining targets directly by month.

The main code is organized as follows:

```text
src/contracts/merchant-stats/
  vocabulary.ts
  views.ts
  quality-copy.ts

src/server/merchant-stats/
  intake/
  attribution/
  apply/
  commands/
  queue/
  read/

src/actions/dashboards/
src/features/dashboards/
src/lib/queries/dashboards.ts
src/routes/(app)/dashboards/
```

`intake/**` is pure. It may import contracts, shared CSV utilities, and
`server/shared/result`, but it must not access the database, clock, apply code,
or read code.

`attribution/**` may use intake types and database types required to load its
context. It must not import from `apply/**` or `read/**`.

`apply/**` coordinates writes and may import from `intake/**` and
`attribution/**`. It must not import from `read/**`.

`read/**` owns dashboard projections and is the only server layer that consumes
`contracts/merchant-stats/views.ts`.

`features/**` may import contracts, queries, actions, and components. It must
not import server modules.

The GPV permissions are:

| Permission            | Access                                                                        |
| --------------------- | ----------------------------------------------------------------------------- |
| `dashboards:read`     | All dashboard panels and the quality summary.                                 |
| `dashboards:read:own` | GPV for RUCs whose current lead belongs to the caller.                        |
| `dashboards:manage`   | Upload reports, resolve attribution, edit targets, and access quality queues. |

Executives only receive `dashboards:read:own`. They can view GPV on records
assigned to them, but cannot open the team dashboards or attribution queues.

The main database objects are:

| Object                         | Key                       | Purpose                                                                       |
| ------------------------------ | ------------------------- | ----------------------------------------------------------------------------- |
| `merchant_reports`             | `id`                      | Accepted report snapshots. `content_sha256` prevents duplicate uploads.       |
| `merchant_report_rejections`   | `(report_id, row_number)` | Rejected source rows stored as JSON.                                          |
| `merchant_sales`               | `id`                      | Merchant devices. Identity is unique by merchant, product, and serial number. |
| `merchant_sale_gpv`            | `(sale_id, month_offset)` | GPV for a device and cohort offset.                                           |
| `merchant_monthly_gpv`         | View                      | GPV grouped by RUC and realized month.                                        |
| `merchant_monthly_attribution` | `(ruc, month)`            | Imported or manually resolved attribution.                                    |
| `merchant_targets`             | `(ruc, effective_from)`   | Effective-dated targets.                                                      |

`MerchantReportId` and `MerchantSaleId` are declared in
`server/shared/ids/registry.ts`. The other tables use composite primary keys and
do not need surrogate IDs.

The import queue uses `createJobQueue` and claims `import_gpv` jobs from
`workflow_integration_jobs`. The records import queue uses the same table but a
different job type, so the runners do not claim each other’s work.

The UI polls `getMerchantReportJob` every 1.5 seconds. When the job completes,
it revalidates the GPV queries.

Uploaded files are stored at:

```text
gpv-reports/${sha256}.xlsx
```

`merchant_reports.storage_key` stores that path. The queue runner reads the
file and passes its bytes to `parseReport`.

The database is disposable. There are no migrations for this module. Schema
changes require updating:

```text
lib/db/schema/modules/merchant-stats.ts
merchant-stats.types.ts
```

Then rebuild and reseed the database:

```bash
bun run dev:infra:setup
```

The demo seed is in:

```text
lib/db/seeds/demo/merchant-stats/persist.ts
```

It imports reports with different cuts, writes effective-dated targets, and
creates examples for `exact`, `inferred`, `conflict`, `late`, `none`,
`no_target`, and `serial_mismatch`.

Manual attribution resolutions and target changes run through audited actions.
`resolveAttribution` also writes a timeline event with:

```text
entity_type = merchant_ruc
type = merchant_attribution_resolved
```
